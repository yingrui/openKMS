# openKMS 的目标与要解决的业务问题

**openKMS 帮助企业快速搭建信得过、可迭代的智能决策系统。**

- **建得快**：AI 把业务逻辑变成能跑的系统——人来定逻辑、做判断，实现和测试交给 AI。
- **信得过**：每个结论都站在企业自己的知识和数据上——依据什么、出自哪里、哪个版本，是否现行、谁定的、谁能改，全都说得清。
- **改得动**：业务改得动逻辑，技术迭代得动系统——改一处口径，就知道哪些决策用了旧版、哪些要复审。

我们卖的不是一套写死的软件，而是搭这类系统所需要的材料、规则、动作，以及让决策靠得住的机制。

## 什么是决策系统 {#goals-decision-systems}

一个案子进来，按规则、看材料和数据，给出一个结论。报关归类、保险核保、质量放行、合规审查，都是这种系统。

它不是文档库，也不是聊天窗口，也不是 BI 报表。它要能回答三件事：凭什么、现在还有效吗、谁负责。

## 为什么现在做不到 {#goals-user-value}

**人这边**：找不到、不敢信、没时间写、过期没人说、答案留在私聊里。

**组织这边** {#goals-organization}：

- 信息散在各处 {#goals-unified-source}：邮件、网盘、老系统、工单各存一份。
- 文档难读 {#goals-documents}：PDF、扫描件、PPT、表格混在一起，机器读不懂，人还得再整理。
- 找不到入口 {#goals-library}：人靠运气翻，agent 更需要清楚的结构。
- 经验留在人脑里 {#goals-tacit}：判断、例外、条件组合都在专家脑子里。
- 规则过期没人知道 {#goals-lifecycle}：政策、法规、合同一变，依赖它的东西都过时了。
- 从“找到”到“能决定” {#goals-decision}：找到一段话不够，还要知道它和对象、数据、规则的关系。
- 给 agent 用 {#goals-agent-service}：agent 需要的不是聊天窗口，是能查、能算、能动手、靠得住的东西。

**同一件事的两面** {#goals-pain-map}：用户觉得“找不到、不敢信、没人管”，组织看到的是“信息散、文档难读、规则过期”。

## 建得快：靠什么

**靠材料现成。** 文档、数据、业务对象和关系本来就在，AI 不用从零开始。

**靠复用。** 第一个项目沉淀成模板，第二个从模板起步。做过一次，下次更快。

要做到这些，需要一条能跑通的建链：**业务逻辑（自然语言）→ 代码/算法 → 测试 → 发布**，以及一个能把这些零件拼起来的地方。

## 信得过：靠什么 {#goals-dependable}

一个决策要信得过，得能回答四个问题：

| 问题 | 要能说清 |
|---|---|
| 依据什么？ | 规则、证据、来源、版本 |
| 现在还成立吗？ | 规则有没有失效、数据是不是最新 |
| 谁有权这么定？ | 负责人、授权范围 |
| 能不能复核、能不能推翻？ | 决策记录、可回滚 |

这四件事不一定要做成四个字段。可以放在业务对象上，可以单独建一个“决策”记录，也可以只记在修改记录里——看业务需要。

## 改得动：靠什么

**靠版本和影响面。** 业务逻辑不是写死的，会改。改了以后，系统要知道：

- 这套逻辑改到第几版了；
- 哪些决策用了旧版；
- 哪些依赖它的东西要复审。

不是“代码好改”，是“改了以后知道影响谁”。这需要三样东西：版本的记录、对象之间的依赖、以及一个复审队列。

## 谁来做

| 角色 | 负责 | 不负责 |
|---|---|---|
| 咨询师/技术 | 搭系统、接数据、做界面 | 拍板 |
| 业务专家 | 定规则、定例外、确认有效 | 写多少字 |
| 业务人员 | 用系统做决定 | 维护系统 |
| 组织 | 权限、依赖、审计、复审 | 天天写内容 |

## 今天缺什么

不是缺一个新对象，是缺两件事：

1. **每次修改能说清“为什么”**：理由、依据、版本、谁改的。
2. **对象能表达“靠得住”**：有版本、有负责人、有有效期、知道谁依赖它。

还有一条链没连起来：知识 → 规则 → 决策 → 运行 → 复审 → 规则变更。每一步我们都有零件，但还没串起来。

## 我们不做什么

- 不是文档库：把文件存起来不是目的。
- 不是聊天窗口：答完就结束，不算决策系统。
- 不是 BI：只出图表，没人对图表负责。
- 不是数字孪生：不把整个企业建出来，只建一个决策需要的那一小片。
